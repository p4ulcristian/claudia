# Claudia for iPhone

A native shell around the hub's page (README decision 23): one full-screen web view on the hub, plus Apple push, the app icon badge, encrypted notification text and a summary Live Activity. The page is the same one browsers get, so page changes need no new build.

- **The page**: a `WKWebView` on the hub, under the status bar; the page pads itself by the safe areas. Cookies and storage persist, so the sign-in survives restarts. The edge swipe goes back through the page's history (chat → chat list). Links to other sites open in the browser; the hub and the sign-in hosts stay in the app. File inputs (photos, camera) are WebKit's own.
- **What the page is told**: before its scripts run, `window.claudiaNative = { platform: "ios", version, build }` (hub origin only, never the sign-in pages). Once APNs gives a token: `window.claudiaNative.pushToken = { token, env, topic, key, liveStartToken? }` and a `claudia-push-token` event on `window` with the same `detail`, again after every page load and whenever a field changes. `env` is `production` for TestFlight and App Store builds and `development` for development-signed ones (read from the embedded provisioning profile); `topic` is the bundle id the build runs under; `key` is base64 of the device key (below); `liveStartToken` is the Live Activity push-to-start token (hex, iOS 17.2 and later), which can come after the rest. The page registers it with the hub.
- **Push**: asks for notification permission on the first launch. A notification's `url` (a path on the hub) opens on tap, also from a cold start. In the foreground, a notification for the chat on screen (its `url`, or its `chat` + `server`, against the web view's address) shows no banner; others do. The hub sends `interruption-level: time-sensitive` for questions and permission asks; it breaks through Focus only once the App ID has the Time Sensitive Notifications capability (switched on in the developer website: the API cannot), and the next build signs with it by itself.
- **Badge**: the hub sends the count in `aps.badge` (also as a badge-only push); the app computes and clears nothing itself.
- **Encrypted notification text**: on the first launch the app makes a 32-byte device key (`SecRandomCopyBytes`) and keeps it in the Keychain group it shares with the Notification Service Extension (`<team>.com.p4ulcristian.claudia.shared`, readable after the first unlock, never logged). The hub seals each notification's real `{title, body}` with it (AES-256-GCM, `enc` = base64 of nonce 12 ‖ ciphertext ‖ tag 16) and sends "Claudia" / "New message" as the visible fallback with `mutable-content: 1`; the extension opens `enc` with CryptoKit and sets the title and body, and on any failure the fallback shows. The rest of the payload (`url`, `server`, `chat`, `kind`) passes through to the tap.
- **Live Activity**: one summary activity, started, updated and ended by the hub by push (push-to-start, iOS 17.2 and later; apns-topic `<bundle id>.push-type.liveactivity`, attributes type `ClaudiaSummaryAttributes`, content state `running`, `waiting`, `done`, `updatedAt`). The lock screen card lists the waiting chats (question or permission) and up to three running ones with the time they have run, and the counts; the Dynamic Island shows the number of running chats, orange, red when something waits on you, and the lists when expanded. A tap opens the waiting chat when exactly one waits, else the chat list (the widget links `claudia://hub/<path>`, the app loads that path on the hub). The app sends each activity's update token to the hub itself, `POST /hub/push/live {device, activity, token}`, and `DELETE /hub/push/live/<activity>` once the activity has ended, with the web view's cookies; iOS starts the app in the background when the hub starts an activity, so this works with no page open. What the hub was told is remembered, so only changes are sent (on launch, on each token or activity change, on each page load and on coming to the foreground).
- **Passkeys**: the sign-in (oauth2-proxy, then Pocket ID) runs inside the web view. WebKit allows WebAuthn there only for a relying party the app is associated with, so the app carries `webcredentials:<Pocket ID host>` and that host must serve `/.well-known/apple-app-site-association` listing `<team id>.com.p4ulcristian.claudia` under `webcredentials.apps`.

## Build and ship to TestFlight

From Linux, Roomprint's recipe: xtool builds, rcodesign signs, the App Store Connect API uploads.

```sh
iphone/tools/testflight.sh              # build, sign, upload (then add the build to a TestFlight group)
iphone/tools/testflight.sh --no-upload  # stop at iphone/build/Claudia.ipa
iphone/tools/asc GET /v1/apps           # any App Store Connect API call with the configured key
```

The build is three bundles (xtool.yml `extensions`, targets in `Package.swift`): the app (`Sources/Claudia`), `PlugIns/Widget.appex` (`Sources/ClaudiaWidget`, the Live Activity, bundle id `com.p4ulcristian.claudia.Widget`) and `PlugIns/NotificationService.appex` (`Sources/ClaudiaNotifications`, bundle id `com.p4ulcristian.claudia.NotificationService`); `Sources/ClaudiaShared` holds what they share (the activity's attributes, the device key).

`testflight.sh` bakes the hub address and the sign-in hosts into the app's Info.plist and gives every bundle the app's version and build number. For each bundle it registers the bundle id when missing, makes or reuses its App Store provisioning profile through the API, and signs it with the entitlements that profile grants (the app: push, the passkey host, the shared Keychain group, Time Sensitive once enabled; the Notification Service Extension: the shared Keychain group; the widget: nothing extra), all in one rcodesign pass.

The icon is `Icon/AppIcon.png`, rendered from `web/app-icon/icon.svg` by `tools/icon.sh`. App Store Connect takes it only from a compiled asset catalog, which only Apple's actool makes: the `app-icon` workflow runs it on a macOS runner when `Icon/AppIcon.png` changes; `tools/fetch-icon.sh` downloads the result into `Icon/compiled/`, which is committed.

## Local config

`~/.config/claudia-ios/` (or `$CLAUDIA_IOS_CONFIG`), never in the repo. `env` holds `HUB_URL`, `LOGIN_HOSTS`, `PASSKEY_HOST`, `ASC_KEY_ID`, `ASC_KEY_FILE`, `ASC_ISSUER_ID`, `ASC_APP_ID`, `DIST_KEY`, `DIST_CER`, `DIST_CERT_ID` and `XTOOL`; the build writes each bundle's profile there (`appstore-app.mobileprovision`, `appstore-widget.mobileprovision`, `appstore-notifications.mobileprovision`).
