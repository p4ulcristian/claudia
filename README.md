# Claudia

Chat with Claude on the left; Claude explains on the right, in a picture it draws as it works. Chat stays short, like two friends talking; the explaining lives in the picture. When Claude asks you something, the right side shows it as buttons.

- Open: `omarchy-launch-webapp http://claudia.localhost:4510/`
- Three services (user units, symlinked into ~/.config/systemd/user), so the page and the runner can restart without stopping chats:
  - `claudia.service` (`server.ts`, :4510): the page, and a pass-through of `/api` and `/ws` to the runner. After edits to `web/`, `server.ts`, `src/proxy.ts`, `src/tunnel.ts`: `systemctl --user restart claudia`. Chats keep running; the page reconnects.
  - `claudia-runner.service` (`runner.ts`, 127.0.0.1:4511): the chats, the chat socket, the API. After edits to `runner.ts` or the rest of `src/`: `systemctl --user restart claudia-runner`. Chats keep running: their Claude Code lives in the host, which hands every live session back.
  - `claudia-host.service` (`host.ts`, `$XDG_RUNTIME_DIR/claudia-host.sock`): the session host, which owns every chat's Claude Code process. Restarting it stops every running chat (the next message resumes it), so it is kept small and rarely changes; after edits to `host.ts` or `src/host-protocol.ts`: `systemctl --user restart claudia-host`.
- `claudia-update.path` + `claudia-update.timer` (+ `claudia-update.service`, `deploy/update-checkout.sh`): on the hub's poke after a push to main (decision 27), and hourly, when GitHub's main moved, fast-forwards this checkout and restarts `claudia-runner` and `claudia`, never `claudia-host` (it says so in `journalctl --user -u claudia-update` when host code changed). A checkout that is not on main, has uncommitted changes or unpushed commits is left alone. Enabled with `systemctl --user enable --now claudia-update.path claudia-update.timer` after linking the three units.
- Dev with hot reload: stop `claudia`, run `bun --hot server.ts` (the runner keeps serving chats)

## Decisions (2026-10-16)

1. Only the owner uses it, on their Claude subscription. (Since 2026-10-20 also a team instance, see 11.)
2. Claude runs through the Claude Agent SDK; drawing is Claude's own tool (`mcp__picture__draw`).
3. The picture is a fixed set of parts (circles, boxes, arrows, groups, and readable cards: text, list, table, code). The app lays them out (ELK) and animates what changed.
4. The picture stays; Claude changes it when a turn changes something. Small talk leaves it.
5. Chats are Claude Code sessions (`~/.claude/projects`), so `claude --resume` and the history window see them. The app keeps only the pictures (`~/.local/share/claudia/app.db`).
6. Every chat runs in `~/Work`, where the full memory lives.
7. A desktop window on my own machine; reachable from elsewhere through a login-gated reverse proxy (`TUNNEL_HOST` + `ALLOWED_EMAIL`).

8. File changes show in a Changes panel on the right: one diff per file per turn. Copies come from a hook before Claude's Edit/Write tools, and from a git snapshot of the working folder's repo (a separate index file; the user's index is untouched), so shell edits count too.
9. A working folder per chat that Claudia tracks (the session itself stays in ~/Work for the full memory): set when Claude first edits a file, or by Claude with `mcp__workspace__set_folder`, any time. See `plan/diffs-and-folders.md`.

10. The subscription is one long-term token (`claude setup-token`) pasted in Settings, kept in a file and read again on every turn; every profile of an instance runs on it, and anyone signed in can replace it (never read it back). A new token applies to each chat on its next message. A long-term token gets no usage readout, so the limits under the input come from the last turn's rate-limit event.

11. Profiles (2026-10-20, `plan/box-and-profiles.md`): the same code runs everywhere; an instance differs only by its settings. The gate's signed-in email picks a profile from the instance's profiles list (`<profile> <email> [runner]`); each profile has its own runner, store, preferences and GitHub login. The desktop window (127.0.0.1) is `CLAUDIA_LOCAL_PROFILE`; the gate's listener (`GATE_HOST`) believes the login header, so only the gate may reach it. `CLAUDIA_NAME` shows under the logo. On a shared server each profile's runner is its own Linux user (`claudia-<profile>`, `deploy/`).

12. A timeline (2026-10-21) in place of the picture (Picture | Timeline at the bottom right, Alt+T): every step of the chat and its subagents as one feed, top to bottom in time order, with a thin rail per agent on the left showing who ran at the same time (rails are reused by later agents); quiet stretches get a divider with their length; a filter shows one agent and the agents it started. Edit and Write steps show their +/− lines and open as a diff, from the patch Claude Code saves with each result (shell edits have none; the Changes panel covers them). Built from the session files themselves (`<session>.jsonl` and `<session>/subagents/agent-*.jsonl` + `.meta.json`), so it survives runner restarts; a step opens in full from its place in the file.

13. A session host (2026-10-22): each chat's Agent SDK query runs in `host.ts`, not the runner. The host knows nothing about Claudia: it streams messages to the runner and passes every callback (the picture and folder tools, the edit hooks, permission asks) to it as an rpc, waiting while the runner restarts. On reconnect it hands back each live session: whether a turn is running, the current turn's messages (plus background tasks' state), what the runner stored there (turn, before-copies of files, unsent messages), and unanswered rpcs, so questions show again.

14. Page cards (2026-10-22): a card can be Claude's own small HTML page (`kind: "page"`, `html`) for what boxes and arrows can't show: charts, sliders, clickable mockups, visual picks. It runs in a sandboxed iframe (`allow-scripts` only: no access to Claudia, its cookies or API), with a CSP that allows only inline code plus scripts/styles from cdn.jsdelivr.net, Claudia's theme as CSS variables, its fonts, and a height fitted to the page. Measured cost: ~1.5k tokens for a page vs ~0.45k for a drawing.

15. Start a chat from a link (2026-10-22): `/new?text=…` opens a new chat of your own (leaving another profile's read-only view) with the text in the message box, not sent; you press Enter. Eye on Rainbow's "Open in Claudia" uses it. A link that sent the text by itself would let any link drive someone's Claude.

16. Asked from outside (2026-10-22): a program that can reach a profile's runner (on the box: the page, and the users its socket's ACL adds, e.g. Eye on Rainbow for its character Gus) starts a chat with `POST /api/delegate {text}` and follows it with `GET /api/chats/:id/state` (running, waiting on a question, last answer, and its newest step, tool count, start and running agents for a progress line); `POST /api/chats/:id/send {text}` adds a follow-up to that chat (2026-10-22). `POST /api/chats/:id/answer {text}` answers its open question(s) in words. The chat is the profile's own, in its sidebar like any other, so the person can open it and steer.

17. The git form (2026-10-22): a repo's history as GitGud showed it (commit graph in lanes, branches local/remote/both with ahead/behind, the uncommitted changes as a dashed node, a commit's files and word-level diff), read live through the runner (`src/git.ts`) and redrawn when the repo's fingerprint changes. Read only: no checkout, branch or fetch buttons; git actions stay in the chat where the user sees them. It is an opt-in form: only runners started with `CLAUDIA_FORMS=git` have it (destiny's runner drop-in); elsewhere Claude doesn't get it and the page doesn't show it.

18. Form row states (2026-10-23): each circle is allowed (default) → required → off. Required means the picture always holds at least one block of that kind: Claude adds it on the next message and draw refuses a change that takes the last one away; the other kinds stay allowed. Off: draw refuses it and its blocks leave the picture. Questions only go allowed ↔ off. Instead of green = "only these kinds", which blocked every other kind with one click.

19. The clojure form (2026-10-23): a Clojure project's namespaces as bubbles in layers from entry points to leaves (an arrow going back closes a circle, drawn red), across or down: by default the direction whose map is closest in shape to its space (the half screen is narrow and scrolls down, full screen is wide), so a deep, thin map runs down; a button flips it, from clj-kondo's analysis run with `--cache false`, so nothing is written into the project (`src/clojure.ts`). A prefix with namespaces under it is one bubble that opens on click, so a 2000-namespace project starts at its top prefixes; a folder of projects (Groundwork) reads each one's `:paths`. A namespace lists its vars (arglists, docs), a var opens its source, an arrow lists the functions that cross it. Re-analysed when a source file changes, one clj-kondo run per project at a time (the last map answers meanwhile); the first read of a big project takes a while (Iron Rainbow: about 25 s). Opt-in like git (`CLAUDIA_FORMS=clojure`), since it needs clj-kondo on the runner.

20. The calls form (2026-10-25): a Clojure project's function calls around one var, as its own form rather than a mode of the clojure form (the user's pick: namespaces and calls answer different questions). Three tabs: Unfold (the var's source; each call to a project var is a link that opens that var's code nested under the calling line, two calls on one line each their own; "called by" chips re-root), Neighbours (the var in the middle, callers left with the exact calling line, callees right with their doc's first line; a path to step back), Map (columns by steps away, default 2 up and 3 down, boxes coloured by folder, arrows for calls, a back arrow curving below; a box opens its code). It shares the clojure form's clj-kondo index (`src/clojure.ts` keeps every use of a project var inside a var, with its row and column), so a project is still analysed once (`src/calls.ts`). A keyword naming a `.sql` file (Iron Rainbow's `(sql/q pool :payment-states …)` runs `payment_states.sql`) links to that file only when the file really exists in the calling namespace's folder. Vars over 40 lines show their first lines and the lines with calls, the rest folded. Opt-in (`CLAUDIA_FORMS=calls`).

21. The editor form (2026-10-25): code Claude and the user both edit, one tab per file, in CodeMirror 6 (a real editor: undo, indent, brackets, search; Dark+ colours like the files form) rather than a textarea over Shiki. The user's typing is saved into the picture as they type (`src/editor.ts`: each file keeps Claude's code and version and the user's unsent text and revision), so a reload or another device keeps it; Claude sees it only on Send. Send hands Claude one message: the user's note, then a `<claudia-code>` per changed file with the diff against Claude's version and the full code; the chat shows a chip per file (`Sent total.ts +3 −1`) that opens the diff. While a file has unsent edits, draw refuses Claude's new code for it and returns the user's code; Claude merges and draws again with `seen` = that revision (a newer edit refuses again). Writable only on the chat's live picture, never read-only views.

22. One UI, many servers (2026-10-28, `plan/one-ui-many-servers.md`): the page is served by a hub (`hub.ts`) on the gate, the one address people open. The hub keeps the servers list and an access grid (person × server; a tick = the person's own profile there, plus a read-only view of the other profiles' chats on it) and passes `/s/<server>/api/…` and `/s/<server>/ws` on to that server over WireGuard, saying who is calling (the header its gate listener already believed). Servers reach nothing new: they keep their page/proxy (`server.ts`), which now also takes whose chats to show from an `X-Claudia-View` header or `?view=` (the socket), and reports its `api` version in `/api/me`. A new server joins with `deploy/pair.sh` (a WireGuard key and a one-time secret printed as a key, pasted into the hub's Servers page; the gate's root helper adds the peer; the server fetches its address with the secret); a person ticked on a server without a profile there waits for `deploy/add-profile.sh` on it: the hub never creates users on servers. On the gate the hub runs from a signed image (`deploy/hub.Dockerfile`, `.github/workflows/hub-image.yml`) with the page built ahead, since the gate is too small to bundle it.

23. An iPhone app with push (2026-10-28, the user's picks, one at a time): a native app, not iOS Web Push for the Home Screen app (which was the 2026-10-22 pick). The app is a native shell around the same page (the hub's), not a SwiftUI client, so there is one front end and page changes need no reinstall; the native part is APNs push and a tap opening that chat (answer buttons on the notification come after). Pushes are sent by the hub, not by each server: the hub learns when a chat finishes a turn, asks a question (AskUserQuestion) or waits on a permission by listening to each server as each person its grid lets in (the calls it already passes on, so servers still reach nothing new), and it holds the APNs key and each person's phone tokens (by gate email) and tells only the people its access grid lets see that chat. The app ships through TestFlight (built on Linux with xtool, as Roomprint does), so Peter and Ananda can install it, rather than xtool's Wi-Fi install to one phone.

    How push works (`src/hub/push.ts`, `src/hub/apns.ts`): for each person with a phone, the hub opens each allowed server's chat socket as them (no view: their own chats only) and reads `/api/chats` on every `chats_changed`, as the page does; each row carries the chat's open questions, permission asks and how its last turn ended (`lastTurn`, kept by the runner; a stopped turn is never told). Each event is told once per person (the hub's store remembers what it told), so a hub restart or reconnect repeats nothing. The page registers the app's token with `POST /hub/push/devices {token, env, topic, key, liveStartToken?}` (`web/native.ts`; `DELETE /hub/push/devices/<token>` removes it); a token APNs calls dead is dropped. Set where the hub runs: `HUB_APNS_KEY_FILE` (the `.p8` key from the Apple developer account), `HUB_APNS_KEY_ID`, `HUB_APNS_TEAM_ID`. Without all three the hub runs without push and says so once in its log; `HUB_APNS_DRY_RUN=1` logs each push instead of sending it (no key needed).

24. Badge, Live Activity, sealed text, phone only when away (2026-10-29, the user's picks):
    - The app icon's badge = the person's chats waiting on them (a question or permission ask) plus chats whose last turn finished since they last opened that chat, across every server the hub lets them use. "Seen" moved from each browser's localStorage to the server (per profile, per chat: the runner keeps each chat's last turn and when it was last open), so the rail's done mark and the badge agree on every device: opening a chat anywhere clears it everywhere. Every alert carries the badge; a change of the count alone goes as a badge-only push.
    - One summary Live Activity per person: while any of their chats runs or waits on them, a lock-screen card and the Dynamic Island with the counts and the chats' titles, started, updated and ended by the hub by push. Live Activity payloads can't be encrypted (iOS reads them), so these titles go through Apple in plain text: accepted.
    - Notification text: a finished turn's body is the start of Claude's last reply, a question's the question; the title is the chat's. Title and body travel sealed (AES-256-GCM under a key the app made), so Apple sees only ciphertext and ids. "Finished" banners stay while the card shows.
    - Phone only when away from the desktop (as Slack does): while the person works at a Claudia page outside the iPhone app (it shows, has the focus, and had input in the last 2 minutes), the hub holds their alerts; badge-only pushes and the card go on. When they leave, it sends what still matters then (questions still open, finished chats still unseen), only the newest per chat; the rest is dropped.

    How it works: the runner's `/api/chats` rows carry `unseen`, the reply's start in `lastTurn.reply`, `runningFor` and each ask's `ago`; the page calls `POST /api/chats/:id/seen` while the open chat shows and is unseen (never in another profile's read-only view). The hub (`src/hub/push.ts`) counts the badge from each person's newest lists, waits 3 s for the count to settle before a badge-only push, and seals alerts with the device's key (`src/hub/seal.ts`, node:crypto; the phone gets `enc` = base64 of nonce, ciphertext and tag, beside a plain "Claudia / New message"). The card (`src/hub/live.ts`, attributes `ClaudiaSummaryAttributes`) starts through the phone's push-to-start token, updates through the token the app reports natively (`POST /hub/push/live {device, activity, token}`, `DELETE /hub/push/live/<activity>` when it sees it end), at most once per 5 s per person (priority 10 only when a chat newly waits), and when nothing runs or waits it shows that at once and ends 30 s later (a follow-up right after a turn keeps the same card), staying 15 minutes on the lock screen. iOS ends a card after 8 hours; one that ended sooner was dismissed, so no new one starts until the next time something runs. Presence (`web/presence.ts` → `POST /hub/presence {page, active}`, `src/hub/presence.ts`; the 2 minutes in `src/presence.ts`): a beat every 30 s while active, "inactive" at once on blur, hide, idle or close; a page silent for 45 s counts as gone. Only pages the hub serves report it: a server's own page (the desktop window) doesn't reach the hub. Held alerts are claimed only when sent or dropped, so a hub restart loses none.

25. Agent chips and "agents working" (2026-10-29, the user's picks):
    - Under the chat's title, a chip per running background agent: subagents and the shells Claude put in the background (not housekeeping tasks; an agent's own shells and agents are part of it). Line 1: its description, elapsed time (ticking), tool count and tokens (tokens only: no cost, no share of a limit); line 2: the step it is on, with its target (`Edit src/hub/push.ts`, `$ xtool dev build`, `WebSearch passkeys WKWebView`), from the newest tool call in its own `subagents/agent-<id>.jsonl` (a shell: its command). Stop on hover. The most recently active show (as many as fit: up to four on a desktop, two on a phone), then "+N more"; finished and failed ones fold into one "✓ N ✕ M" chip. Both open the list of every agent of the chat. File changes stay in the pill; agents left it.
    - A chip opens the agent's view in the chat column, like a chat: ‹ Back to the chat (on a phone a history entry, so the back swipe closes it), its facts (status, time, tools, tokens, model and effort, agent type, worktree branch and its commits), and tabs: Steps (its transcript, live), Files (its Edit and Write calls by file with +/−, each opening its diff; for an agent in its own git worktree also the branch's commits and the whole change since the branch was made, read only), Prompt (from the Agent call in the chat's file) and Report (its result). A shell's view has its output and command.
    - A third rail state: Claude's turn ended but work it started still runs: a dashed amber ring with the count, not the working dots; ✓ only once the turn ended and none runs. The same moment holds the hub's "Finished" push and the badge's unseen: rows carry `agents` (the running count), `unseen` stays false while any runs, and when the last ends with no turn running the chat waits 5 s (30 s once a turn's init came) for the turn its notice usually starts; if none starts, the last turn's time moves to then, so it is unseen again and told once (its turn id is still the claim). If the notice starts a turn, that turn's end is told as before. The Live Activity counts such a chat as running.

    How it works: `src/agents.ts` builds the list from the session files (the chat's own: Agent calls, background Bash calls, task notifications and results; each subagent's: its steps, model, tokens and edits) and the runner's live tasks, served at `GET /api/chats/:id/agents` (`?v=` as the timeline's), `/agents/:agent` (prompt, report, files, branch), `/agents/:agent/steps` and `/agents/:agent/git` (the git form's commit view on the agent's branch only). A subagent's file keeps no patch of its edits, so their counts and diffs come from the calls' input (numbered within the replaced text). `src/working.ts` says which tasks count, for the runner and the page alike; the page polls every 2 s while one runs. A chat's Claude Code no longer closes when idle while work it started runs (that ended the work), and a task whose process went is marked stopped.

26. Only chats in the list, Settings behind a gear, swipes that follow the finger (2026-10-29, the user's picks: the phone's list had too much on it, and its swipes between list, chat and picture barely worked):
    - The list (the phone's list screen and the desktop's opened sidebar) holds only chats: a header (whose chats as the title, the 5-hour and week usage as two small rings, a gear), a search field, the rows, and + for a new chat (a phone: floating bottom right; a desktop: in the header). Everything else is on a Settings screen the gear (or the rings) opens: archived chats, sounds, desktop popups, all ~/Work sessions, forms, the instance chip, the plan bars with their reset times, the hub's admin pages and each server's own settings. On a phone Settings is a screen of its own with ‹ Chats (a history entry); on a desktop it takes the sidebar's place. The desktop rail stays as it was.
    - A row: the chat's circle (the rail's, with its state: working, agents working and how many, waiting, done), title, server mark (hub with two servers or more), time; under it what the chat does while it works or waits ("Claude working · 2 agents", "Agents working · 2", "Asks you: …", "Needs your permission: Bash"), else the start of Claude's last reply. Another person's chats look the same, with a small lock.
    - In the hub the title is a menu: whose chats (yours, or another person's, read only) and a tick per server (an unticked server's chats leave the list; the last ticked one stays). The title says what shows: "My chats", "Peter's chats", plus "· <the server>" or "· 2 servers" while some are unticked. No tabs or filter row on the list.
    - Phone swipes follow the finger, as iOS's back swipe does: on the chat, right slides it off over the list (which comes in from 30% to the left) and left pulls the picture in; on the list, left slides the open chat back over it (back's mirror, added after the user found the list couldn't be swiped shut); on the picture, right pushes it out; on Settings and an agent's view, right goes back. Released past 40% of the width, or flicked, it completes; else it springs back. The page owns the gesture (the iPhone app turns iOS's own edge swipe off): it starts anywhere, not only at the edge, except in fields, on what moves sideways itself (code and tables that scroll, the picture's pannable graphs, sliders), with two fingers, or on a mostly vertical move (the axis is decided on its first 10 px). The screens keep their history entries, so the browser's back and the app's back still work. With reduced motion nothing follows the finger: a completed swipe just switches.

    How it works: `web/sidebar.tsx` (the list, the title menu, Settings), `web/chatdot.tsx` (the circle the rail and the rows share), `web/swipe.ts`, `web/sidebar.css`. On a phone the chat lies over the list (both full screen) and Settings over the list in the sidebar. A drag changes only inline transforms, once a frame; on release they are animated to where the screen's classes put it, the app steps (through history, as the buttons do), and the inline styles go once the classes show the end. `web/viewport.ts` still decides on a touch's first move whether anything native moves; a swipe takes a drag only when nothing does (`touchBlocked()`), so a scroller and a swipe never both follow one finger. The rows read `asks`, `permits` and `lastTurn` from `/api/chats` (decision 24). Unticked servers are kept per browser.

27. Every machine follows main, started by the gate (2026-10-30, the user's picks, one at a time): GitHub's webhook for this repository goes to the hub (`POST /hub/github`, no login, signed with a shared secret, `src/hub/github.ts`). A push to main pokes every server (`POST /api/update-check` on its gate listener, `server.ts`), which writes `CLAUDIA_UPDATE_TRIGGER`; a path unit then starts its update (destiny: `claudia-update.path` and `deploy/update-checkout.sh`; a shared server: `deploy/claudia-update.path` and `deploy/update.sh`). A finished hub-image run on main makes the hub ask the gate's root helper to update the hub to that run's commit (the gate repo's `flatcar/claudia-hub/update.sh`); the gate updates the hub itself rather than destiny deploying it, so it works while destiny is off. The hub image is public, so the gate pulls with no credential. A poke only says "look now": each machine fetches main, and the gate checks the image's signature (this repository's hub-image workflow on main) and moves only forward. The update timers stay, hourly, for a poke that was missed.
28. Any file can be attached (2026-10-30, the user's ask): photos and videos still go as images (`web/media.ts`); every other file, and a photo the browser can't draw (HEIC, SVG), is sent to the chat's server as soon as it is added (`POST /api/chats/:id/uploads`, up to 100 MB, with progress) and saved in the runner's data folder, `uploads/<chat>/<name>` (`src/uploads.ts`). The message carries a `<claudia-file>` tag per file after the user's text (`src/attached.ts`) and Claude reads the file at its path; the chat shows the tags as file chips that download the file. Files are dropped anywhere in the window, pasted, or picked with the paperclip; a dropped folder is refused. A file stays as long as its chat: its messages point at it.

Questions use Claude Code's own AskUserQuestion tool. Permission mode matches the terminal: bypass. The few calls bypass still sends to the permission callback (its own safety checks) are allowed and logged by the runner, so no permission ask shows; only questions and plan approval reach the user.

## Progress bars

A background shell whose output has a `##progress <done>/<total> <label>` line shows a bar on its agent chip
(`src/progress.ts` reads the last such line from the task's output file; the 2 s agents poll carries it).
`bin/claudia-progress` wraps any command and prints the line after each output line matching a regex.

## Files

- `server.ts`: the page; picks the profile and passes `/api` and `/ws` to its runner; the gate's listener
- `hub.ts`: the hub on the gate: the page, servers and access grid (`src/hub/store.ts`), pairing (`src/hub/pairing.ts`), `/s/<server>/…` pass-through, phone pushes (`src/hub/push.ts` watches the servers, alerts and the badge, `src/hub/live.ts` the Live Activity, `src/hub/seal.ts` seals alert texts, `src/hub/presence.ts` who is at a desktop, `src/hub/apns.ts` sends; `web/native.ts` the page's side in the iPhone app, `web/presence.ts` a desktop page's presence)
- `host.ts`: the session host; `src/host-protocol.ts` what it and the runner say; `src/host-client.ts` the runner's end
- `runner.ts`: chats, WebSocket, chat list, rename, archive
- `src/proxy.ts`: request and socket pass-through (page → runner, by port or unix socket)
- `src/profiles.ts`: which profile a request is, where its runner listens; the Claude token file
- `src/mode.ts`: what sets an instance apart: token file, name
- `src/github.ts`: the profile's GitHub login (gh), used for pushes and pull requests
- `src/chat.ts`: one chat = one Agent SDK session; turns, questions, stop, history
- `src/prompt.ts`: what Claude is told about the two halves, and the draw tool
- `src/scene.ts`: the picture's parts and how a draw call changes them
- `src/changes.ts`: before/after copies, git snapshots, diffs
- `src/account.ts`: the Claude token the chats run on
- `src/meta.ts`: models, slash commands and plan limits, read by a short probe
- `src/db.ts`: pictures, changes and chat settings
- `src/attached.ts` + `src/uploads.ts`: files attached to a message, saved per chat (decision 28)
- `src/forms.ts`: the predefined forms; `src/files.ts`, `src/git.ts` (+ `src/git-layout.ts`), `src/clojure.ts` and `src/calls.ts` read for the files, git, clojure and calls forms; renderers in `web/forms.tsx`, `web/git.tsx`, `web/clojure.tsx`, `web/calls.tsx` and `web/flow.tsx`
- `src/timeline.ts`: lanes and steps from the session files, read only from where the last read stopped
